# 基线：框架开销（2026-10-22）

这是 `ss-benchmark` 在**一台机器**上的第一份基线，用来以后做回归对比和回答"某个开关值不值得开"。
**它测的是框架本身的开销，不是你们系统的容量**：空处理器、回环、明文、64 字节，没有业务逻辑、数据库、真实网络、TLS、Aeron。
怎么运行、各列含义、局限见 [README.md](README.md)；原始结果是 [baselines/2026-10-22-apple-m5-pro-18core-jdk25.txt](baselines/2026-10-22-apple-m5-pro-18core-jdk25.txt)。

## 环境

| | |
|---|---|
| 机器 | Apple M5 Pro，18 核（6 个性能核 + 12 个能效核），64GB，接市电 |
| JDK | OpenJDK 25.0.3（Zulu），服务端 `-Xms1g -Xmx1g`，客户端 `-Xms512m -Xmx1g`，默认 G1 |
| 被测代码 | `ss-grpc-server-starter` 2026.10.21.0（Spring Boot 4.1.1、Spring gRPC 1.1.1、grpc-java 1.83.1） |
| 负载 | 客户端和服务端在**同一台机器**，各占掉十几个核；后台还有别的进程（一个虚拟机进程约占 0.3 个核、IDE、浏览器） |

## 先看结论

1. **Spring + 本 starter 本身几乎没有开销**：关掉观测后与原生 grpc-java 的差别约 1%（吞吐 −1.3%，每请求 CPU +3.4%，
   后者在噪声边缘），P99 相同。
2. **观测（指标 + 追踪）约多花 10µs CPU / 请求，吞吐约 −5%，P99 +10% 左右（约 +0.15ms）**。
   按这个数粗算，约每 10 万 QPS 多占 1 个核。
3. **直方图桶、追踪采样率（0.1 对 1.0）在噪声里分不出差别**：四种带观测的配置每请求 CPU 在 157.7 到 159.7µs 之间，
   只差 2µs（1.3%），小于 5% 的噪声下限（见"怎么相信这些数字"）。别在这两项上花精力优化。
4. **单条连接在回环上能跑到约 8.6 万 QPS（只占 3.4 个核）**，所以单条连接不是瓶颈；同一台机器上 **2 条连接最好**
   （9.8 万 QPS、P99 最低），连接越多越差（16 条连接时 P99.9 超过 120ms）。这是同机争抢核的结果，**不能推广到客户端和服务端分开的机器**。
5. 约 10 万 QPS 是**这台机器**的饱和点（并发 32 附近，服务端约 13 个核），不是服务端的上限。

## 怎么相信这些数字

- **噪声**：同一次启动内的窗口之间很稳定；真正的噪声来自**不同次服务端启动**之间（JIT 编译、GC 布局不同）。
  原生对照的每请求 CPU 在三次启动里是 138.2 / 146.1 / 147.1µs，相差 6%；QPS 相差约 1%。
  所以：**QPS 差 2% 以内、每请求 CPU 差 5% 以内，不要当成变化**
- **一个教训**：最早一次只启动一次服务端的运行得出过"直方图桶几乎没有额外开销，指标约 7µs"；
  第二次独立运行显示"无桶的指标几乎免费，有桶多出 13µs"，两者矛盾。改成每个配置启动 3 次、交错排列后，
  结论变成上面第 3 条（四种配置没有可分辨的差别）。**单次启动的 A/B 对比不可信**，这个工具默认就是多次启动交错
- 启动 `run-all.sh` 前的构建会让 Mac 的负载很高，第一个实验的头几次测量可能受影响；需要更干净的数据，
  可以先构建一次，等机器安静下来再跑
- 其余局限见 [README.md](README.md#局限读结果时请记住)：追踪没有配置导出地址，所以**没测发送开销**；
  压测客户端是原生 grpc-java，**没有**客户端 starter 的开销

## 怎么用这份基线

改动 starter 之后，在**同一台机器**上跑 `ss-benchmark/bin/run-all.sh`，它会自动和 `baselines/` 里最新的基线对比，
表末尾的"QPS变化"和"CPU变化"列就是相对基线的差别。重点看：

- `obs-off` 对 `raw`：我们的代码有没有在热路径上变慢（基线上约 1%）
- 带观测的配置对 `obs-off`：观测的开销有没有变大（基线上约 +10µs / 请求）
- 换了机器、JDK 或 Spring Boot 大版本后，先建立新的基线，再比较
